# ECFS 자동화 — 03_제출확정자료 파일 기반 추출 계획 (SOP)

> **성격**: 계획 문서(설계안). 아직 구현하지 않았다. `sop.md`(현행 ECFS 자동화 SOP)의 후속 Phase로 편입될 예정.
> **작성 근거**: 「폴더구조_설계서」§5(사건 폴더 5단계), 「서류별_추출필드_정의표」, `ecfs_fill_engine.js`(payload 스키마), 기존 n8n 워크플로우 「ECFS 자동화 트리거」.
> **결정된 방향**(사용자 확정):
> 1. 원본 = **03_제출확정자료 안의 모든 파일을 명칭 무관 전부 참고**(엄선 확정본이므로). AI가 종합.
> 2. 추출 = **n8n의 AI 노드**가 수행(오피스 서버엔 LLM 없음).
> 3. 폴더 접근 = **Google Drive API**.
> 4. 개인정보 = **암호화해 주고받음** + 주민번호는 외부 AI 미전송(로컬 추출·마스킹).
> 5. 검증 게이트 = **admin 프리필**(법무사 검토·확정). Notion = **파일 우선 + 상태만 되쓰기**.

---

## 1. 목적과 배경

현재 `/run-full-from-notion`은 사건부DB→고객/상대방DB 관계를 읽어 당사자 payload를 구성한다. 이를 바꿔, **`03_제출확정자료` 폴더의 확정 문서에서 직접 전자소송 정보를 추출**해 payload를 만든다.

바꾸려는 이유: 03은 "실제로 낸 그 버전"이 동결되는 폴더(설계서 §5-다)이므로, 제출 서면 자체가 당사자·청구취지·청구원인의 가장 정확한 단일 원본이다. Notion 관계 입력이 누락·미정이어도 확정 신청서만 있으면 자동화가 가능해진다.

바꾸지 않는 것: 인증서 로그인·전자서명·최종 제출은 여전히 사람(안전경계, §6). 실행 상태와 법원사건번호는 계속 Notion에 기록한다.

## 2. 목표 아키텍처

```
admin(사건번호 입력·실행)
   │  웹훅(secret 인증)
   ▼
n8n 워크플로우  ECFS 파일추출 자동화
   ├ [1] 사건 폴더 탐색     사건번호 → Google Drive에서 폴더 찾기 → 03_제출확정자료
   ├ [2] 전체 자료 수집     03 안의 모든 파일(명칭 무관) 수집 — 확정 엄선본
   ├ [3] 문서 텍스트화       docx/pdf/이미지 → 텍스트 (스캔은 OCR)
   ├ [4] AI 노드 추출        전체 텍스트 → 구조화 JSON(payload 초안)   ★핵심
   ├ [5] 검증·정규화         필수필드·주민번호 13자리·주소 구조화·금액 정합
   ├ [6] 사람 검증 게이트    법무사가 admin 프리필 화면에서 검토·수정·확인   ★안전경계
   ├ [7] Notion 락 마킹      전자소송자동화상태 = 진행중
   └ [8] 서버 호출          /run-full (구조화 payload) → Playwright ecfs 구동
   ◀ 콜백                   Notion 상태·법원사건번호 되쓰기

   ※ 개인정보(주민번호·주소)는 전 구간 암호화하고, 외부 AI 노출은 최소화한다(§4.5).
```

기존 「ECFS 자동화 트리거」 워크플로우(웹훅→사건부DB 조회→락→서버 호출, 현재 비활성)를 재사용·확장한다. 달라지는 핵심은 **[1]~[5] 파일 탐색·AI 추출 구간이 "사건부DB 관계 조회"를 대체**한다는 점이다. Notion은 [7]·콜백(상태 기록)에서만 쓴다.

## 3. 추출 대상 → payload 매핑

목표 스키마는 현행 `ecfs_fill_engine.js`의 `runFullFlow` payload와 **동일하게 유지**한다(서버·오케스트레이터를 안 건드리기 위함).

| payload 필드 | 원본(03 문서) | 추출 주체 | 위험도/주의 |
|---|---|---|---|
| `caseBasicInfo.caseName` (사건명) | 확정 신청서 표제 | AI [4] | 폴더명 사건명과 대조 |
| `caseBasicInfo.claimType` (청구구분) | 신청서 유형 | AI [4] + 법무사 확인 [6] | 재산권상/비재산권상 |
| `caseBasicInfo.litigationValue` (소가) | 신청서 청구금액 | AI [4] + 법무사 확인 [6] | 🔴 법적판단 — 부대청구 불산입 등 |
| `caseBasicInfo.courtName` (관할법원) | 신청서 표제 | AI [4] + 법무사 확인 [6] | 🔴 관할 판단 영역 |
| `parties[].name / orgName` | 신청서 당사자표시 | AI [4] | 🟡 등본·인감과 교차확인 |
| `parties[].ssnFront/ssnBack` | 신청서 당사자표시 | AI [4] + 정규화 [5] | 🔴 13자리 대조 필수 |
| `parties[].address`(시도/시군구/도로명/본번) | 신청서 당사자 주소 | AI [4] + 법무사 확인 [6] | 🔴 **구조화 분리** — 오분리 시 송달 오류 |
| `parties[].contact`(mobile/phone/email) | 신청서·상담내용 | AI [4] | 상담내용에서 보완 |
| `claim.purposeText` (청구취지) | 신청서 본문 | AI [4] | 원문 보존 원칙 |
| `claim.reasonHtml` (청구원인) | 신청서 본문 | AI [4] | 2,000자 초과 시 별지 분기(기존 로직) |
| `evidence[]` (소명서류) | 03의 첨부/호증 파일 | 파일 유형 판별 [2] | 명칭 무관 · PDF/이미지 파일을 소명서류 후보로 |

> **원본 선택 방식(확정)**: 03_제출확정자료에는 접수수집·작업자료 중 **꼭 필요한 것만 엄선된 확정본**만 들어간다. 따라서 파일 명칭으로 신청서를 고르지 않고, **03 안의 모든 파일을 명칭과 무관하게 전부 읽어** AI가 종합한다. 그중 신청서 성격 문서에서 당사자·청구취지·청구원인을, PDF/이미지 첨부는 소명서류(evidence)로 판별한다.

**핵심 원칙**: `caseBasicInfo`·`claim`·구조화 주소는 기존에도 "자동 추측 금지" 영역이었다(fill engine이 명시적으로 막음). 이번 설계에서도 AI가 **초안만 만들고**, 소가·관할·주소는 [6] 사람 검증 게이트에서 법무사가 확정한다.

## 4. 단계별 상세

### [1] 사건 폴더 탐색 — Google Drive
- 입력: 사건번호(예 `260722_01`).
- 폴더는 `법무사업무/사건/<카테고리>/<사건번호>-고객명-사건명/03_제출확정자료/` 형태로 6개 카테고리 하위에 흩어져 있다.
- **Google Drive API** 노드로 접근한다(법무사업무는 드라이브 미러링). 사건번호 prefix(`260722_01-`)로 폴더를 검색해 `03_제출확정자료`를 찾는다. 드라이브 루트/공유드라이브 ID를 설정값(`CASE_DRIVE_ROOT`)으로 둔다.

### [2] 전체 자료 수집 (명칭 무관)
- 03_제출확정자료에는 접수수집·작업자료 중 **꼭 필요한 것만 엄선된 확정본**만 저장된다. 따라서 **폴더 안의 모든 파일을 명칭과 무관하게 전부** 가져온다(신청서 파일명 규칙에 의존하지 않음).
- 파일 유형만 구분한다: 텍스트형 문서(신청서·상담내용 등) → [4] AI 추출 입력, PDF/이미지 첨부 → 소명서류(evidence) 후보.

### [3] 문서 텍스트화
- `.docx`: 본문 텍스트 추출(문단 단위).
- `.pdf`(텍스트형): 텍스트 추출 / (스캔형): OCR.
- 이미지: OCR. 신청서는 보통 텍스트형이라 신뢰도 높다.

### [4] AI 노드 추출 (n8n)
- 03에서 모은 **전체 텍스트를 함께** AI 노드에 넣고, **출력 스키마(JSON)를 §3 payload 구조로 고정**한다(function/structured output). 여러 문서를 종합해 하나의 payload 초안을 만든다.
- 프롬프트 원칙: "여러 문서에 있는 값을 종합해 추출, 없으면 null. 추측 금지. 금액은 원문 그대로. 주소는 가능한 범위에서 시도/시군구/도로명/본번으로 분리하되 불확실하면 `addressRaw`만 채우고 `needsManualAddressSplit=true`."
- **개인정보 최소화**: 주민번호는 AI에 보내지 않고 로컬 정규식으로 별도 추출한다(§4.5).
- 사용 모델·자격증명은 §4.5의 개인정보 요건을 만족하는 것으로 선택.

### [5] 검증·정규화
- 주민번호: 숫자 13자리로 정규화(`splitSsn` 규칙 재사용). 아니면 flag.
- 금액: 숫자화, 부대청구(이자·지연손해금) 소가 불산입 여부는 [6]에서 확인.
- 필수필드 누락·주소 미분리를 **차단 플래그**로 표시(기존 `needsManualAddressSplit`·`representativeMissing`·법인 원고 미지원 규칙 그대로 승계).

### [6] 사람 검증 게이트 (안전경계)
- AI 추출은 항상 "⚠️ 미검증". **법무사 확인 없이는 실제 포털에 입력하지 않는다.**
- 통합 방식(택1, §7) — 권장은 **A**:
  - **A. admin 프리필**: 추출 payload를 admin 「전자소송 신청」 폼에 채워 보여주고, 법무사가 소가·관할·주소·청구취지를 검토·수정 후 `자동신청 시작`. (기존 화면 재사용, 사람 통제 유지)
  - **B. 사건폴더 JSON**: n8n이 `03_제출확정자료/ecfs_payload.json`을 저장 → admin이 로드·검토.
  - **C. n8n 승인 노드**: n8n Wait/Approval로 법무사 승인 후 진행.

### [7] Notion 락 마킹
- `전자소송자동화상태 = 진행중`으로 잠금(중복 실행 방지). 기존 트리거 워크플로우 로직 재사용.

### [8] 서버 호출
- n8n이 **구조화 payload**를 서버 `/run-full`로 전달(사건부DB 관계 조회 없이).
- **서버 코드 변경 거의 없음(확인됨)**: `/run-full`은 이미 `payload`(caseBasicInfo·parties·claim·evidence)와 `사건_page_id`(상태 되쓰기용)를 함께 받는다. 즉 Notion 상태·법원사건번호 되쓰기 배관이 이미 존재한다.
- n8n은 사건번호 → 페이지 id를 이번에 추가한 조회 기능(`findCaseByNumber` / `GET /resolve-case`)으로 얻어 `사건_page_id`에 넣으면 된다. 서버는 그대로 Playwright ecfs 흐름을 구동하고 콜백에서 상태를 기록한다.

---

### [4.5] 개인정보 암호화·최소화 (확정 요건)

주민번호·주소 등 개인정보는 "암호화해서 주고받는다"는 요건을 다음 세 층으로 구현한다.

- **전송 구간 암호화(in transit)**: n8n ↔ 자동화 서버, admin ↔ 서버, Google Drive 접근 등 **모든 네트워크 홉을 TLS(HTTPS)로** 암호화한다. n8n이 다른 PC/서버에 있으면 서버에 인증서를 붙여 `https`로 호출한다(같은 PC localhost 홉은 네트워크에 노출되지 않음).
- **AI 노출 최소화**: **주민번호는 외부 AI에 보내지 않는다.** 주민번호는 형식이 고정(`\d{6}[-. ]?\d{7}`)이라 로컬 정규식으로 결정적으로 추출하고, AI에는 주민번호를 마스킹(예: `██████-███████`)한 텍스트만 보낸다. AI는 이름·주소·청구취지·원인 등만 추출하고, 주민번호는 로컬 추출값을 payload에 합친다.
- **필드 단위 암호화 + 무평문 로그**: n8n→서버 payload의 민감 필드(주민번호·주소)는 공유키로 필드 암호화해 전달하고 서버가 사용 직전 복호화한다. 감사 로그·`last_state.json`에는 **주민번호를 평문으로 남기지 않는다**(마스킹 저장). ※ 이는 앞서 지적한 vercel 공개 노출 정리와도 연결된다.

> 권장: LLM 자체도 학습 미사용·무보존(zero-retention) 정책의 엔드포인트를 쓰고, 위 마스킹과 병행한다. 마스킹만으로도 주민번호는 외부로 나가지 않는다.

## 5. 단계별 로드맵 (Phase)

| Phase | 내용 | 산출물 |
|---|---|---|
| **A. 폴더·문서 파이프라인** | 사건번호→Google Drive에서 03 탐색 + 03 전체 파일 수집 + 텍스트화(OCR 포함) | n8n [1]~[3] 노드, `CASE_DRIVE_ROOT` 설정 |
| **B. AI 추출 + 개인정보 보호** | 주민번호 로컬 정규식 추출·마스킹 → AI 노드(§3 스키마 고정) → 검증·정규화 | n8n [4]~[5]·[4.5], payload 초안 |
| **C. 사람 검증 게이트** | admin 프리필 연결(추출 payload를 「전자소송 신청」 폼에 채움) | 추출→폼 프리필 경로 |
| **D. 상태 되쓰기·파일럿** | 사건번호→page_id(`/resolve-case`)로 상태 되쓰기 연결 + 더미 사건 1건 종단 테스트 | 파일럿 로그 |
| **E. 보완** | 첨부(PDF/이미지) 소명서류 자동 매핑, 필드단위 암호화·무평문 로그 마무리 | evidence 자동 채움, 암호화 완료 |

각 Phase는 독립 검증 가능하게 나눴다. A~B는 실제 포털을 건드리지 않으므로 안전하게 먼저 완성한다.

## 6. 안전 원칙 (기존 §7 그대로 유지)

- 인증서 로그인·전자서명·최종 제출·납부는 **자동화 대상 아님**(사람).
- AI 추출값은 **미검증**이며, [6] 법무사 확인 전에는 실제 포털 입력 금지.
- 소가·관할·주소 구조화는 자동 확정하지 않고 법무사가 확정(오분리 시 송달·관할 오류 위험).
- 사건번호가 연결 키. 03 폴더·payload·Notion 상태 모두 사건번호로 대조.
- **원본 불변**: 03 파일은 읽기만 한다. 쓰기(예: `ecfs_payload.json`)는 03의 확정본을 건드리지 않도록 별도 파일로 둔다.
- **개인정보 암호화·최소화**(§4.5): 전송 구간 TLS, 주민번호는 외부 AI 미전송(로컬 추출·마스킹), 로그 무평문.

## 8. 기존 문서와의 정합성 점검

- **폴더구조 설계서 §5**: 03은 "제출확정·동결·읽기 전용 성격". 본 계획은 03을 **읽기만** 하므로 원본 불변 원칙과 충돌 없음.
- **fill engine payload**: 스키마를 그대로 유지하므로 서버·오케스트레이터·개별 스킬 변경 없음(진입 데이터 소스만 교체).
- **기존 안전경계**: 자동 서명·제출 금지 원칙 유지. 새로 완화하는 경계 없음.
- **Notion 단일관리(개인정보)**: 주민번호 등은 03 확정본(이미 사건폴더에 존재)에서 읽어 payload로만 쓰고, PC에 새 평문 사본을 남기지 않는다(§6 원본 불변과 일치). AI 노드 전송 이슈는 §4.5의 **주민번호 로컬 추출·마스킹**으로 해소한다(주민번호는 외부 AI로 나가지 않음).

### 구현·검증 완료
| 산출물 | 내용 |
|---|---|
| `ecfs_privacy.js` | 주민번호 로컬 정규식 추출·⟦주민번호N⟧ 마스킹·토큰 되채움·정규화. 오타(`651010. 1910615`)까지 처리. 단위테스트 통과 |
| `ecfs_file_payload.js` | AI raw + 토큰맵 → fill-engine payload 조립·검증(주소 미구조화·소가·법인원고·주민번호 누락 경고). 단위테스트 통과 |
| 서버 `POST /privacy/mask` | 텍스트의 주민번호를 마스킹해 반환. **AI엔 masked만 전달** → 주민번호가 오피스 서버 밖으로 안 나감 |
| 서버 `POST /build-prefill` | AI raw+tokens → payload 조립 + 프리필 저장 |
| 서버 `POST/GET /prefill` | n8n 추출결과 ↔ admin 프리필 브릿지 |
| admin 「전자소송 신청」 | `🗂️ 파일 추출 불러오기` 버튼 → 폼(사건기본정보·청구)·당사자(JSON 검토) 프리필 → 검토·수정 후 실행 |
| admin 실행 분기 | 프리필 있으면 **파일 기반 `/run-full`**(Notion 당사자 매핑 안 씀), 없으면 기존 Notion `/run-full-from-notion` |

### n8n 워크플로우가 호출할 HTTP 계약(완성됨)
```
1. (n8n) Google Drive: 사건번호로 03_제출확정자료 전체 파일 읽기 → 텍스트화
2. (n8n) POST /privacy/mask { text }            → { masked, tokens }
3. (n8n) AI 노드: masked 텍스트 → raw(JSON, 주민번호는 ssnToken 참조)
4. (n8n) POST /build-prefill { 사건번호, raw, tokens } → 프리필 저장
5. (사람) admin 「파일 추출 불러오기」 → 검토·확정 → 실행(/run-full)
```

### n8n 워크플로우 (2026-07-25 생성, 2026-07-28 종단 디버깅 완료)
- **워크플로우 v3**: 「ECFS 파일기반 자동추출 v3 (docx→PDF 변환 포함)」 id `EQfdtsk4etlJ1PLe` (박배선 개인 프로젝트). v1·v2는 보관. **폼 실행 → 서버 `/build-prefill` 저장까지 종단 동작 확인**(2026-07-28, 부동산 명도 실사건 `260724_01-한국벨브`).
- **노드 흐름(23노드)**: 폼(사건번호·서버주소) → 사건폴더 찾기 → 03 폴더 찾기 → 파일목록 → **파일유형 분기**(PDF / GoogleDoc / **docx** / 기타) → 다운로드·텍스트추출 → 합류 → 취합 → `POST /privacy/mask` → Gemini 정보추출 → `POST /build-prefill`.
- **docx 분기**: docx 다운로드 → **base64 변환(Code)** → PDF.co 업로드 → PDF.co Convert to PDF → PDF 내려받기 → PDF 텍스트추출.
- **자동 연결된 자격증명**: Google Drive·PDF.co·Gemini. HTTP 노드는 인증 불필요.
- **03 폴더 자동 탐색**: 03 폴더 ID를 넣지 않는다. 사건번호로 사건폴더를 찾고 그 안 `제출확정`을 포함하는 하위 폴더를 자동으로 찾는다(폴더 ID가 사건마다 달라도 됨).

### 종단 실행 중 발견·해결한 이슈 (2026-07-28)
| 증상 | 원인 | 해결 |
|---|---|---|
| PDFco 업로드 "Base64 Content required" | 워크플로우 binary 모드가 `separate`라 표현식으로 base64를 못 얻음 | docx 다운로드 뒤에 **base64 변환 Code 노드**(`getBinaryDataBuffer`) 삽입 → PDF.co Base64 Content = `{{ $json.base64 }}` |
| 서버 URL 깨짐 | 폼 기본값 앞에 공백(` https://…`) | 취합 노드에서 `서버base`를 `.trim()` |
| 03 폴더 찾기 0건 | 폴더명 exact-match(`name = '03_제출확정자료'`)가 실제 폴더명과 미세하게 달라 미매칭 | `name contains '제출확정'`으로 완화 |
| 정보 추출 `"[object Object]" is not valid JSON` | informationExtractor `jsonSchemaExample`에 객체를 넣음(문자열이어야 함) | JSON **문자열**로 교체 |

### 실행 전 사용자가 채울 것 / 유의점
- **오피스 서버 공개주소**: n8n 클라우드는 오피스 localhost에 못 닿으므로, 오피스 PC에서 `ngrok http 3939`로 공개 URL을 만들어 폼 「자동화 서버 공개주소」에 입력(서버는 `3_start_server.bat` 실행 중이어야 함). ngrok 무료 주소는 재시작마다 바뀜.
- **hwp 한계**: hwp는 Google·PDF.co 모두 자동 변환 불가 → 03에는 PDF/Google Doc/docx로 저장.
- **법인 원고**: 추출·프리필은 되지만 당사자 자동입력(party-input)은 개인 원고만 지원 → 법인 원고 사건은 admin에서 법무사가 직접 처리.
- **AI 추출 품질**: `claimType`에 사건명이 들어가는 등 일부 값은 부정확할 수 있음 → 소가·관할·청구구분은 admin 프리필 화면에서 법무사가 최종 확정(사람 검증 게이트).
- **공유 드라이브**: 03 폴더 검색이 안 될 경우, `법무사업무`가 공유 드라이브에 있으면 상위폴더 쿼리 검색 범위(드라이브 스코프) 조정이 추가로 필요할 수 있음.
- **참고**: tokens(주민번호 실값)는 n8n↔서버 사이에서만 오가고 외부 AI엔 마스킹만 전달된다.
